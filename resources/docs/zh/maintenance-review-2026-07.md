# 可维护性审查报告（2026-07）

## 本轮结论

项目的模块依赖方向基本正确，租户隔离、统一充值记录、运行时链配置和确认状态闭环已经形成。当前主要维护成本不来自模块数量，而来自少数超大服务/仓储、Job 层遗留业务逻辑、开关判定分散以及前端缺少统一请求缓存。

本轮已完成以下收敛：

- 扫描周期集中到 `WalletRuntimeConfigService`，Account-Chain 与 UTXO 共用一份按链策略。
- 调度器改为轻量到期检查，未到期链不访问 RPC。
- 总开关、全局任务开关和链任务开关继续由数据库实时判定，不增加本地配置缓存。
- 托管提现在冻结资金前强制校验运行时提现开关。
- XMR 从通用账户链扫描调度中排除，避免与独立串行任务重复扫描。
- console GET 请求增加 10 秒短缓存和并发去重，写操作统一失效缓存，后台刷新保留已有内容。
- console 路由继续懒加载，并增加稳定 vendor 分包与 Shell 派生数据记忆化。
- console 充值、提现、地址、审计和资产找回列表统一采用服务端分页，前端只加载并渲染当前页。

## 风险与发现

| 优先级 | 发现 | 影响 | 建议 |
|---|---|---|---|
| P0 | `UtxoBatchJob` 位于 `wallet-api`，但包含选币、锁 UTXO、计算手续费、创建交易和状态推进 | 违反薄 Job 边界，难以单测和复用 | 将主体迁入 `wallet-api` 内部的 UTXO 工作流服务，Job 只保留 `service.run(chain)` |
| P0 | `AccountChainWorkflowService` 同时编排十余条链，接近单体链路由器 | 新增链或修改一条链容易影响其他链 | 按 family 建立 `AccountChainHandler` 注册表，工作流只做遍历、开关和错误隔离 |
| P0 | `ChainJdbcRepository` 聚合配置、充值、提现、UTXO、地址和 checkpoint 等多类数据访问 | 修改 SQL 的影响范围过大，审查困难 | 按领域拆为 `ChainProfileRepository`、`DepositRepository`、`WithdrawalRepository`、`UtxoRepository`、`ScanCheckpointRepository` |
| P1 | 部分链服务通过可选注入运行时开关，非 Spring 构造路径可能绕过底层校验 | 安全边界依赖调用方自律 | 保留工作流入口硬校验，逐步将链网关改为必须注入或只暴露包内方法 |
| P1 | UTXO 提现和归集共用批处理描述，但当前入口主要按提现开关控制 | 开关语义容易与真实订单类型不一致 | 在迁移 UTXO 工作流时按订单业务类型分别判定 withdraw/collection，再合并可兼容的链上输出 |
| P1 | `transfer` 开关已进入配置模型，但通用跨链转账能力尚未形成统一入口 | 配置项含义容易被误解 | 明确 transfer 仅控制已实现的主动转账能力；新增链能力时必须从统一执行服务进入 |
| P1 | 多处状态字符串直接写在 Java 和 SQL 中 | 拼写错误只能在运行期发现 | 收敛为领域枚举，并由 Repository 统一完成数据库字符串映射 |
| P2 | console 大型详情页同时承担查询、表单、弹窗和表格列定义 | 重渲染范围大，修改成本高 | 按独立数据区拆组件，列定义使用 `useMemo`，大列表启用服务端分页或虚拟滚动 |
| P2 | console 当前使用轻量自研查询 Hook | 缓存策略、失效范围和竞态需要自行维护 | 页面规模继续增长时引入单一查询库；在此之前保持缓存逻辑集中在 API client |
| P2 | 扫描周期是代码内集中策略，不支持后台调参 | 调整周期仍需发布 | 只有出现明确运营需求后再增加 `scan_interval_ms`，避免过早扩张配置面 |

## 开关语义

| 阶段 | 关闭后行为 |
|---|---|
| 新充值扫描 | 停止访问链 RPC 和写入新扫描结果 |
| 新提现创建/构建/广播 | 阻止进入新的资金冻结或链上动作 |
| 新归集/主动转账 | 阻止创建新的链上动作 |
| 已广播交易确认 | 继续更新确认数和最终状态 |
| 对账、回调、reorg 处理 | 继续执行，保证账务闭环 |

这一语义避免“关闭业务开关”变成“停止观察已经发生的资金动作”。如果需要事故级硬停机，应单独设计 emergency stop，并明确其对广播队列和在途交易的处理方式。

## 推荐优化顺序

1. 将 `UtxoBatchJob` 业务逻辑迁入 `wallet-api` 内部业务服务，消除当前最明确的分层违规。
2. 拆分 `ChainJdbcRepository`，优先拆充值和扫描 checkpoint，再拆提现/UTXO。
3. 为账户链建立 handler 注册表，移除中心服务中的大型 `switch`。
4. 统一状态枚举、任务开关判定入口和审计事件模型。
5. [已完成] console 大表已统一服务端分页；后续仅在单页数据量确实超过渲染阈值时引入虚拟列表。
6. 建立调度与开关契约测试，覆盖运行中关闭、重新开启、链级关闭和在途确认不中断。
